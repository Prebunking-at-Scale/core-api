-- Simulate the redesigned alert system (D0-D8) against the database.
-- Returns every narrative that WOULD carry a badge, with both axes and the badge.
--
-- Run it as-is: calc_date is the LAST COMPLETED SCRAPING DAY (yesterday), compared
-- against the day before. This mirrors production -- the pipeline defaults to
-- date.today() - 1 for exactly this reason (core/narratives/service.py:725, and the
-- docstring above it): acceleration is driven by videos scraped ON calc_date, so scoring
-- a part-scraped day leaves current == prev and hands almost everyone a zero.
--
-- Do NOT set calc_date = CURRENT_DATE to "avoid the erosion" below. It buys an honest
-- denominator by measuring a different quantity -- a part-day's growth over whatever
-- subset the scraper has reached so far -- which is not what the system computes and not
-- what production would badge.
--
-- Optional second run, as a cross-check only: CURRENT_DATE / CURRENT_DATE - 1 gives an
-- un-eroded cohort for a partial day. The gap between its cohort size and the default
-- run's is the most direct read on the erosion available -- but read it as a diagnostic
-- about the data, not as a preview of the badges.
--
-- ============================================================================
-- WHAT IS SIMULATED FAITHFULLY (settled decisions)
-- ============================================================================
--   D0  composite pool = measured at least once; acceleration pool = visited on
--       calc_date (videos.updated_at::date, NOT video_stats -- it is a change log)
--   D3  composite ranked over the full ~22k pool, not the ~2-3k dashboard cohort
--   D5  visited-but-flat narratives stay in, ranked at an honest zero
--   D6  viral = high composite AND high acceleration
--   D7  composite = engagement_pct*0.625 + reach_pct*0.375   (velocity dropped)
--
-- Also fixed here, per the "reach mixes data sources" defect: BOTH sides of
-- reach_score come from video_stats. Production divides a video_stats numerator by a
-- videos-table denominator.
--
-- ============================================================================
-- WHAT IS A GUESS -- CHANGE THESE AND RE-RUN, THAT IS THE POINT OF THE QUERY
-- ============================================================================
--   O2/O3  boundary_composite / boundary_accel are PLACEHOLDERS. They cannot be
--          derived from data; they are the product call this query exists to inform.
--
--          MEASURED 2026-07-17, first run: at 0.80/0.50 this badged all 2237 narratives
--          in the cohort (409 of them `viral`). boundary_accel = 0.50 is meaningless on
--          this axis -- 42.5% sit at exactly zero, median accel is 0.000024 and p90 is
--          0.0215, so 0.50 selects "anything above the zero block", including narratives
--          that grew 0.002%. The signal lives in the top 1-2%: p99 = 1.39.
--          Start at boundary_accel = 0.98 and work down. And note that a percentile that
--          high is an absolute threshold wearing a costume -- which is D2's rejected
--          option, so if it works that is a finding about D2.
--   O5.5   NEW VIDEOS -- SETTLED. Two rules, both at the NARRATIVE level then the video:
--
--          1. The narrative must have had videos the day before. A narrative with none was
--             CREATED on calc_date -- that is birth, not acceleration -- and is excluded
--             (the INNER JOIN to narrative_prev).
--          2. A video the narrative gained counts as growth if it is GENUINELY NEW:
--             uploaded within new_video_max_age_days (7) of calc_date. An older video the
--             scraper merely discovered does not count -- the narrative did not gain it,
--             our knowledge did. uploaded_at IS NULL counts as new.
--
--          change_video_count is restored at its production weight, since under rule 2 it
--          now measures real new content rather than scraper sweep.
--
--          NOTE: the design doc's O5.5 was wrong to say "the schema forecloses telling
--          them apart". True of claim_narratives (no created_at, so the LINK cannot be
--          dated), but uploaded_at dates the UPLOAD, which is what rule 2 needs.
--   O8     the GREATEST(0.0, ...) floor is KEPT (current behaviour). It merges decliners
--          with genuinely flat narratives, which D0 arguably forbids. Delete the
--          GREATEST() to see decliners rank below flat ones.
--   D4     per-day normalisation is NOT implemented. Growth is not divided by each
--          video's elapsed gap, so a video measured after 4 days still contributes 4
--          days of growth as if it were 1. D4 will move these numbers.
--
-- ============================================================================
-- OPTIONAL SECOND RUN -- measures the discovery contamination.
-- ============================================================================
-- Run as-is (new_video_max_age_days = 7), then again with it set to NULL, which disables
-- the age test and counts every new video the way the pre-O5.5 behaviour did.
--
-- The gap between the two is how much of the alert stream was the scraper finding old
-- videos rather than narratives spreading. Under D10's geometry the NULL run fires 333
-- narratives, 247 of them (74%) on gained videos. If the 7-day run fires far fewer, most
-- of that 74% was sweep. If it fires about as many, the gained videos really are new
-- content and the alert stream was honest all along.
--
-- Watch `videos_gained` in the output. If it collapses to ~0 everywhere, uploaded_at is
-- probably NULL or unreliable across the corpus and the age test is doing nothing
-- meaningful -- check before drawing any conclusion from the comparison.
-- ============================================================================
--
-- ============================================================================
-- KNOWN LIMITATION: this DEGRADES for a past calc_date, it does not fail cleanly.
--
-- The visit predicate below unions permanent evidence (a video_stats row on calc_date --
-- append-only, never decays) with ephemeral evidence (videos.updated_at::date =
-- calc_date -- overwritten by the next scrape). So for an older calc_date:
--
--   movers  (>=1 video changed that day)  -> RECOVERED in full. Permanent evidence.
--   flat    (visited, nothing changed)    -> ERODED, and completely gone once every one
--                                            of the narrative's videos is re-scraped.
--
-- The default calc_date (yesterday) is ~1 day into that decay, so expect SOME of the flat
-- population to be missing already. What that does, precisely:
--
--   * The ORDER of narratives on the acceleration axis is CORRECT. Every mover is
--     present with its true raw `accel`, and dropping zeros from the bottom does not
--     reorder anything above them.
--   * The `accel_pct` VALUES are INFLATED. Missing zeros shrink the denominator, so every
--     surviving narrative ranks higher than it should.
--
-- So: trust the mover list, the raw `accel` column, and the ranking order. Treat the
-- badge counts as an OVER-estimate -- an inflated accel_pct pushes narratives over
-- boundary_accel that production would not have promoted. Do not fix O2/O3 from this run.
-- ============================================================================

WITH params AS (
    SELECT
        CURRENT_DATE - 1      AS calc_date,   -- last COMPLETED scraping day, as production
        CURRENT_DATE - 2      AS prev_date,
        -- D7 composite weights
        0.625::float AS w_comp_engagement,
        0.375::float AS w_comp_reach,
        -- acceleration weights, per D9. Acceleration measures SPEED OF DISTRIBUTION;
        -- engagement is a MODIFIER on it and must not be able to overturn it.
        -- Production ships 0.40/0.35/0.25, where engagement (0.40) outweighs views (0.25)
        -- and cancels the growth it is meant to modify -- see D9 in the design doc.
        -- The only hard constraint is w_acc_engagement < w_acc_views.
        0.10::float  AS w_acc_engagement,
        0.35::float  AS w_acc_video_count,
        0.55::float  AS w_acc_views,
        -- NEW VIDEOS (O5.5). A video first seen on calc_date counts as the narrative's
        -- growth, provided the NARRATIVE itself has a baseline AND the video is genuinely
        -- new: uploaded within this many days of calc_date. An older video the scraper
        -- merely discovered is not growth -- the narrative did not gain it, we just
        -- learned it existed.
        --
        -- A video with uploaded_at IS NULL is treated as NEW: missing platform metadata
        -- is not evidence the video is old, and a video should not be penalised for it.
        --
        -- Set to NULL to disable the age test entirely (counts every new video) -- for
        -- diagnostics only; the difference between 7 and NULL is the discovery
        -- contamination.
        7::int       AS new_video_max_age_days,
        -- from core/narratives/service.py:45-46 and core/config.py:74
        1.0::float   AS likes_weight,
        5.0::float   AS comments_weight,
        10.0::float  AS reach_cap,
        5.0::float   AS change_cap,
        -- O3 geometry, read off the source diagram (Captura de pantalla 2026-07-16).
        -- Six thresholds, not two -- the regions are RECTANGLES, not quadrants:
        --   viral        red    composite >= 0.8  AND  accel >= 0.8
        --   early_surge  orange composite <= 0.4  AND  accel >= 0.5   (SMALL and climbing)
        --   consolidated blue   composite >= 0.5  AND  accel <= 0.4
        --   trending     yellow composite >= 0.4  AND  accel >= 0.4, minus viral
        --   (no badge)   white  everything else -- the bottom-left
        0.40::float  AS comp_lo,    -- early_surge ceiling / trending floor
        0.50::float  AS comp_mid,   -- consolidated floor
        0.80::float  AS comp_hi,    -- viral floor
        0.40::float  AS accel_lo,   -- consolidated ceiling / trending floor
        0.50::float  AS accel_mid,  -- early_surge floor
        0.80::float  AS accel_hi    -- viral floor
),
links AS (
    SELECT DISTINCT cn.narrative_id, v.id AS video_id
    FROM videos v
    JOIN video_claims c      ON c.video_id = v.id
    JOIN claim_narratives cn ON cn.claim_id = c.id
),

-- ---------------------------------------------------------------- COMPOSITE (D0/D3/D7)
-- Pool: measured at least once. Carry-forward is legitimate for a *level*.
state AS (
    SELECT DISTINCT ON (l.narrative_id, l.video_id)
           l.narrative_id, l.video_id, vs.views, vs.likes, vs.comments
    FROM links l
    JOIN video_stats vs ON vs.video_id = l.video_id
    WHERE vs.recorded_at::date <= (SELECT calc_date FROM params)
    ORDER BY l.narrative_id, l.video_id, vs.recorded_at DESC
),
narrative_state AS (
    SELECT narrative_id,
           count(*)                         AS videos,
           COALESCE(sum(views), 0)::float    AS views,
           COALESCE(sum(likes), 0)::float    AS likes,
           COALESCE(sum(comments), 0)::float AS comments
    FROM state
    GROUP BY narrative_id
),
avg_views AS (
    SELECT avg(views) AS avg_views FROM narrative_state WHERE views > 0
),
comp_scores AS (
    SELECT ns.*,
        CASE WHEN ns.views > 0
             THEN (ns.likes * (SELECT likes_weight FROM params)
                 + ns.comments * (SELECT comments_weight FROM params)) / ns.views
             ELSE 0 END                                          AS engagement_score,
        CASE WHEN (SELECT avg_views FROM avg_views) > 0
             THEN least(ns.views / (SELECT avg_views FROM avg_views),
                        (SELECT reach_cap FROM params)) / (SELECT reach_cap FROM params)
             ELSE 0 END                                          AS reach_score
    FROM narrative_state ns
),
comp_ranked AS (
    SELECT *,
        PERCENT_RANK() OVER (ORDER BY engagement_score) AS engagement_pct,
        PERCENT_RANK() OVER (ORDER BY reach_score)      AS reach_pct
    FROM comp_scores
),
composite AS (
    SELECT *,
        (SELECT w_comp_engagement FROM params) * engagement_pct
      + (SELECT w_comp_reach FROM params)      * reach_pct        AS composite
    FROM comp_ranked
),
composite_ranked AS (
    SELECT *, PERCENT_RANK() OVER (ORDER BY composite) AS composite_pct
    FROM composite
),

-- ------------------------------------------------------------- ACCELERATION (D0/D4/D5)
-- Pool: >=1 video VISITED on calc_date. This is the D0 predicate and the whole point.
-- "Provably visited on calc_date" -- the union of a permanent record and an ephemeral
-- one. Neither alone is enough:
--
--   (a) a video_stats row on calc_date PROVES a visit (create_video always writes one;
--       update_video writes one when the numbers moved). video_stats is append-only, so
--       this evidence NEVER decays -- it is as good in six months as it is today.
--   (b) videos.updated_at::date = calc_date proves a visit that changed nothing. This
--       evidence DOES decay: the column holds only the last visit, so it is overwritten
--       the moment the video is scraped again.
--
-- Union recovers everything except: visited, nothing changed, AND re-visited since.
-- That residue is exactly the visited-but-flat population -- i.e. `consolidated`. So the
-- decay is NOT neutral, it eats the honest zeros first. See D0 / O6.
visited AS (
    SELECT DISTINCT l.narrative_id
    FROM links l
    JOIN videos v ON v.id = l.video_id
    WHERE v.updated_at::date = (SELECT calc_date FROM params)      -- (b) decays
    UNION
    SELECT DISTINCT l.narrative_id
    FROM links l
    JOIN video_stats vs ON vs.video_id = l.video_id
    WHERE vs.recorded_at::date = (SELECT calc_date FROM params)    -- (a) permanent
),
prev_state AS (
    SELECT DISTINCT ON (l.narrative_id, l.video_id)
           l.narrative_id, l.video_id, vs.views, vs.likes, vs.comments
    FROM links l
    JOIN video_stats vs ON vs.video_id = l.video_id
    WHERE vs.recorded_at::date <= (SELECT prev_date FROM params)
    ORDER BY l.narrative_id, l.video_id, vs.recorded_at DESC
),
narrative_prev AS (
    SELECT narrative_id,
           count(*)::float                   AS video_count,
           COALESCE(sum(views), 0)::float    AS views,
           COALESCE(sum(likes), 0)::float    AS likes,
           COALESCE(sum(comments), 0)::float AS comments
    FROM prev_state
    GROUP BY narrative_id
),
-- Current state for the acceleration numerator. Three cases:
--
--   1. Baselined video (seen on or before prev_date)  -> ALWAYS counts. It has two
--      observations, so its change is measurable.
--   2. No baseline, uploaded within new_video_max_age_days of calc_date -> COUNTS. The
--      narrative genuinely gained a video; that is real growth and the strongest
--      early_surge evidence there is.
--   3. No baseline, uploaded longer ago than that      -> EXCLUDED. The scraper merely
--      discovered an old video. The narrative did not gain it; our knowledge did.
--
-- uploaded_at IS NULL falls in case 2 -- treated as new. Missing platform metadata is not
-- evidence a video is old.
--
-- videos.uploaded_at is written on ingest and already trusted for this kind of reasoning
-- (core/narratives/repo.py:314 ranks a narrative's videos by upload date;
-- core/videos/repo.py:364 computes views/sec since upload).
state_for_accel AS (
    SELECT s.narrative_id, s.video_id, s.views, s.likes, s.comments,
           (p.video_id IS NOT NULL) AS had_baseline
    FROM state s
    LEFT JOIN prev_state p
           ON p.narrative_id = s.narrative_id AND p.video_id = s.video_id
    JOIN videos v ON v.id = s.video_id
    WHERE p.video_id IS NOT NULL                               -- 1. baselined
       OR (SELECT new_video_max_age_days FROM params) IS NULL  -- age test disabled
       OR v.uploaded_at IS NULL                                -- 2a. unknown -> assume new
       OR v.uploaded_at::date >= (SELECT calc_date FROM params)  -- 2b. genuinely new
                                 - (SELECT new_video_max_age_days FROM params)
),
narrative_cur_accel AS (
    SELECT narrative_id,
           count(*)                                                  AS cur_videos,
           count(*) FILTER (WHERE had_baseline)                      AS videos_baselined,
           COALESCE(sum(views), 0)::float                            AS views,
           COALESCE(sum(likes), 0)::float                            AS likes,
           COALESCE(sum(comments), 0)::float                         AS comments
    FROM state_for_accel
    GROUP BY narrative_id
),
-- INNER JOIN to narrative_prev is the bright line: if the NARRATIVE had no videos the day
-- before, it was created on calc_date and there is nothing to compare against -- that is
-- not acceleration, it is birth. Those narratives drop out here. A narrative that HAD
-- videos and gained more is measurable, and its new videos are counted as growth.
accel_raw AS (
    SELECT
        vi.narrative_id,
        nc.cur_videos,
        nc.videos_baselined,
        np.video_count AS prev_videos,
        nc.views AS cur_views,
        np.views AS prev_views,
        CASE WHEN nc.views > 0
             THEN (nc.likes * (SELECT likes_weight FROM params)
                 + nc.comments * (SELECT comments_weight FROM params)) / nc.views
             ELSE 0 END AS cur_eng,
        CASE WHEN np.views > 0
             THEN (np.likes * (SELECT likes_weight FROM params)
                 + np.comments * (SELECT comments_weight FROM params)) / np.views
             ELSE 0 END AS prev_eng
    FROM visited vi
    JOIN narrative_cur_accel nc ON nc.narrative_id = vi.narrative_id
    JOIN narrative_prev      np ON np.narrative_id = vi.narrative_id
),
accel AS (
    SELECT narrative_id, cur_videos, videos_baselined, prev_videos, cur_views, prev_views,
        least(CASE WHEN prev_eng > 0 THEN (cur_eng - prev_eng) / prev_eng ELSE 0 END,
              (SELECT change_cap FROM params))                    AS change_engagement,
        least(CASE WHEN prev_videos > 0 THEN (cur_videos - prev_videos) / prev_videos ELSE 0 END,
              (SELECT change_cap FROM params))                    AS change_video_count,
        least(CASE WHEN prev_views > 0 THEN (cur_views - prev_views) / prev_views ELSE 0 END,
              (SELECT change_cap FROM params))                    AS change_views
    FROM accel_raw
),
accel_scored AS (
    SELECT *,
        greatest(0.0,                                    -- O8: delete to unfloor declines
              (SELECT w_acc_engagement FROM params)  * change_engagement
            + (SELECT w_acc_video_count FROM params) * change_video_count
            + (SELECT w_acc_views FROM params)       * change_views
        ) AS accel
    FROM accel
),
accel_ranked AS (
    SELECT *, PERCENT_RANK() OVER (ORDER BY accel) AS accel_pct
    FROM accel_scored
)

-- --------------------------------------------------------------------- CLASSIFY (D1/D6)
-- Only the acceleration cohort is classifiable. Every label makes a claim about today
-- ("climbing", "flat"), and we cannot make that claim about a narrative we did not look
-- at. Composite's ~22k pool exists to give a stable RANK, not to badge more narratives.
SELECT
    ar.narrative_id,
    n.title,
    cr.videos                                AS videos_all,      -- composite's video count
    ar.prev_videos::int                      AS prev_videos,     -- had a baseline
    ar.cur_videos                            AS cur_videos,      -- baselined + new-and-counted
    (ar.cur_videos - ar.videos_baselined)    AS videos_gained,   -- the new ones accel counts
    cr.views::bigint                         AS views_all,       -- composite's number
    ar.cur_views::bigint                     AS cur_views,       -- accel's numerator
    ar.prev_views::bigint                    AS prev_views,      -- accel's denominator
    round(cr.composite::numeric, 4)          AS composite,
    round(cr.composite_pct::numeric, 4)      AS composite_pct,
    round(ar.accel::numeric, 6)              AS accel,
    round(ar.accel_pct::numeric, 4)          AS accel_pct,
    round(ar.change_engagement::numeric, 6)  AS change_engagement,
    round(ar.change_video_count::numeric, 6) AS change_video_count,
    round(ar.change_views::numeric, 6)       AS change_views,
    -- Order matters: viral is carved OUT of the trending box, so it must be tested first.
    CASE
        WHEN cr.composite_pct >= (SELECT comp_hi FROM params)
         AND ar.accel_pct     >= (SELECT accel_hi FROM params)   THEN 'viral'
        WHEN cr.composite_pct <= (SELECT comp_lo FROM params)
         AND ar.accel_pct     >= (SELECT accel_mid FROM params)  THEN 'early_surge'
        WHEN cr.composite_pct >= (SELECT comp_mid FROM params)
         AND ar.accel_pct     <= (SELECT accel_lo FROM params)   THEN 'consolidated'
        WHEN cr.composite_pct >= (SELECT comp_lo FROM params)
         AND ar.accel_pct     >= (SELECT accel_lo FROM params)   THEN 'trending'
        ELSE NULL                                    -- the white region: no badge
    END                                     AS would_be_alert_level,
    n.alert_level                           AS current_alert_level
FROM accel_ranked ar
JOIN composite_ranked cr ON cr.narrative_id = ar.narrative_id
JOIN narratives n        ON n.id = ar.narrative_id
ORDER BY ar.accel_pct DESC, cr.composite_pct DESC;

-- NOTE ON 'trending': as written every narrative in the acceleration cohort gets one of
-- the four labels -- there is no "no badge" region. The doc's D1 calls trending "the
-- broad middle" but never says whether the middle is a badge or an absence. If most of
-- the cohort comes back `trending`, that is the question surfacing, not a bug. It needs
-- deciding (and it is adjacent to the unresolved grey-diagonal caveat in D3).
